# 版本与分支规范

- `main` 是自维护集成主分支；`origin/main` 是原作者上游，`yorick/main` 是本分支远端。上游更新先在合并分支解决冲突并完成检查，再合入自己的 `main`。
- 尚未验收的专项修复留在独立分支。`fix/tool-images-compaction` 的原始长上下文问题仍待验证，不随本次上游合并进入 `main`；`dmit/allowed-emails` 上独有的 ultra 映射也未纳入。
- 版本唯一来源是 `internal/basispoints/types.go` 的 `Version`。采用 `X.Y.Z-alpha.N`（开发验测）、`X.Y.Z-beta.N`（功能范围收敛）、`X.Y.Z-rc.N`（发布候选）、`X.Y.Z`（正式版）。各数字不加前导零，预发布序号从 1 递增。
- 普通提交、重编译和部署不自动改版本；提交 SHA 标识代码快照。只有准备新的可分发候选包时才递增预发布序号，并同步更新 `CHANGELOG.md`。已分发候选包改变内容也必须递增。
- 正式版按兼容性选择主版本、次版本或补丁版本；预发布提升需有对应验收记录。合并上游后记录上游 tag/commit，不能据此声称本分支已通过上游的部署验收。
- 发布 tag 必须为 `v${Version}`，且在两个远端都未被占用。历史 tag 和产物不重命名、不强制移动、不覆盖；不再新增 `dmit`、`search`、`draft`、`images`、`deploy` 等临时版本后缀。
- CI 检查版本格式、当前 changelog 条目、tag 一致性；alpha/beta/rc 发布标记为 prerelease，不能成为正式版 latest。创建 tag、发布和部署是单独步骤，合并主分支不会部署生产。

本次集成基线为上游 `v0.1.18` / `11df6f8`，本分支候选版本为 `0.1.19-alpha.1`。
原有生产动态库的名称和版本保持历史记录，不因本规范改名。

部署前查询宿主实际加载的插件版本、文件路径和摘要；不要依赖目录中的文件名推断版本。
当前 CPA 宿主对预发布版本并非完整 SemVer 排序（例如 `alpha.10` 与 `alpha.9`），
部署时必须明确选择目标文件并核对实际加载结果，不能依赖多个候选库的自动排序。
